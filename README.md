# retrieval-eval

A small harness that answers one question with numbers instead of opinion:
**does each step of a typical RAG retrieval stack actually improve retrieval, and by how much?**

```
BM25  ->  dense  ->  hybrid (RRF / weighted)  ->  hybrid + cross-encoder rerank
```

All results are in [RESULTS.md](RESULTS.md), generated by `run.py`. No number in this README or in RESULTS.md is typed by hand.

## Headline

On 648 FiQA test queries, with every setting chosen on the separate dev split:

| | nDCG@10 | Recall@10 | p95 latency |
|---|---|---|---|
| Before: BM25 | 0.251 | 0.318 | 3 ms |
| After: hybrid, 0.7 dense + 0.3 BM25 | **0.415** | **0.479** | 21 ms |
| Change (95% CI) | +0.163 [+0.143, +0.184] | +0.162 [+0.136, +0.188] | |

What the ladder showed:

- **Dense retrieval did most of the work** (+0.152 nDCG@10 over BM25).
- **Hybrid added a small but real gain** over dense alone (+0.011, CI [+0.003, +0.020]), but only with the weight tuned on dev.
  Untuned RRF fusion was *worse* than dense alone (0.362 vs 0.403): a weak lexical signal dragged it down.
- **The reranker was rejected.** The general-purpose MS MARCO cross-encoder lowered dev nDCG@10 from 0.420 to 0.380, so it was not shipped.
  The test split confirms it: -0.039 nDCG@10, worse on 213 queries and better on 136, at about 30x the median latency (333 ms vs 11 ms).
  A reranker is a common default; here the numbers said no.
- **BM25 sanity check:** 0.251 here vs 0.236 published by BEIR with a different BM25 implementation. Close enough to trust the pipeline.

## Dataset and labels

[BEIR](https://github.com/beir-cellar/beir) **FiQA-2018**: personal finance and investing questions.

- Corpus: 57,638 StackExchange posts from the Investment topic, 2009-2017 (BEIR paper, appendix D.2).
- Queries: 648 test and 500 dev questions, sampled by BEIR from FiQA's original training split.
- **Labels are not mine.** They are FiQA's binary question-to-document matches, published with the
  [FiQA 2018 challenge](https://sites.google.com/view/fiqa/). On average a test question has 2.6 relevant posts.
- Known weakness: these are community-sourced matches, so some genuinely relevant posts are unlabelled.
  This lowers absolute scores for every system equally; it matters less for comparing systems on the same queries.

## Method

| Step | What it is |
|---|---|
| BM25 | `bm25s`, English stopwords + Snowball stemmer, title + text |
| Dense | `BAAI/bge-small-en-v1.5`, normalised embeddings, exact dot-product search, bge query instruction on queries only |
| Hybrid RRF | Reciprocal rank fusion of the BM25 and dense top-100, k = 60 |
| Hybrid weighted | Per-query min-max normalised scores, `alpha * dense + (1 - alpha) * bm25` |
| Rerank | `cross-encoder/ms-marco-MiniLM-L-6-v2` re-scores the top 50 of the better hybrid |

Rules that keep the comparison honest:

1. **Choices are made on dev, scores are reported on test.** `alpha` is picked from a grid of 0.0 to 1.0 on the 500 dev queries,
   and RRF vs weighted, and whether to keep the reranker, are chosen the same way. The test split is never used to pick anything.
2. **Every number comes with uncertainty.** 95% bootstrap confidence intervals over queries (10,000 resamples, fixed seed).
3. **Every step is tested against the previous one** with a paired bootstrap over the same queries, so a gain is only claimed
   when it survives resampling.
4. **Metrics are checked against a reference.** `metrics.py` matches `pytrec_eval` (recall@10, nDCG@10) to within 1e-15 on
   randomised runs, and has hand-calculated self-checks.
5. **Sanity check against published work.** BEIR reports BM25 nDCG@10 = 0.236 on FiQA (Table 2, Anserini BM25).
   This harness uses a different BM25 implementation, so a small gap is expected; a large one would mean a bug.

Metrics: Recall@10, MRR@10 and nDCG@10 (pytrec_eval definitions), plus per-query latency p50 / p95.

## Run it

```bash
uv sync
uv run python run.py      # downloads FiQA (~17 MB) and two small models, ~10-15 min on an Apple M4
```

Outputs: `RESULTS.md`, `results/results.json`, `results/per_query.csv` (every test query, every config, for error analysis).

Self-checks: `uv run python metrics.py` and `uv run python retrievers.py`.

## Files

| File | Lines | Role |
|---|---|---|
| `data.py` | ~60 | Download and load FiQA from the official BEIR archive |
| `retrievers.py` | ~165 | BM25, dense, RRF, weighted fusion, reranker, with a self-check |
| `metrics.py` | ~100 | Recall / MRR / nDCG, bootstrap CI, paired bootstrap, with a self-check |
| `run.py` | ~220 | The ladder, dev tuning, latency, report |

## Limitations

- One dataset, one language, small models chosen to run on a laptop. Larger embedding and reranking models would score higher;
  the point is the method, not the leaderboard.
- Latency is measured one query at a time in one process on an Apple M4, so it shows relative cost, not production throughput.
- Retrieval only. Answer quality (faithfulness, grounding) needs a separate evaluation.
